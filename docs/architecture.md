# 分层与请求链路

本文描述该应用的结构分层与一次网络请求的完整链路，用于配合 `REPORT.md` 第 2～4 节阅读。

---

## 1. 安装包构成

```
数百 MB 级混合架构安装包
├── 主 DEX            ← 复合体：少量壳类 + 大量"内容仍在、索引已毁"的填充
├── 资源与资源表
├── 签名信息          ← 自有签名别名
├── 原生库（三套 ABI）
│   ├── 商用加固组件           （加密实现的一部分在这个 SDK 里）
│   ├── 自研 JNI 库            （对称原语 / 摘要 / 密钥表 / 若干业务判定）
│   ├── 跨平台运行时 + 业务 AOT （跨平台侧逻辑不在这条 JVM 工具链上）
│   ├── 地图导航、播放器
│   └── 机器学习模型相关
└── assets
    ├── 加固组件的数据文件与配置
    ├── 跨平台资源
    └── 模型与地图资源（体积主要来源）
```

结论：体积构成不等于安全构成。占体积最大的是地图、播放器与模型；安全相关的只有加固组件与那一个自研 JNI 库。

---

## 2. 运行时分层

```
┌───────────────────────────────────────────────────────┐
│ 加固壳的 Application                                  │
│   ├─ 还原业务代码 → 以内存形态交给虚拟机              │
│   └─ 加载自研 JNI 库后就地还原其数据段常量            │
├───────────────────────────────────────────────────────┤
│ 业务 App（原生页面 + 跨平台页面）                     │
├───────────────────────────────────────────────────────┤
│ 网络层：拦截器链                                      │
│   ├─ 日志拦截器                                       │
│   └─ 加解密拦截器                                     │
│        ├─ 策略判定（按接口注解 / URL 白名单兜底）      │
│        ├─ 头部签名（会话级）                          │
│        ├─ 业务体签名 + 体加密                         │
│        └─ 响应解密                                    │
│              ↑ 加解密原语来自加固 SDK；摘要与盐来自自研 JNI 库
└───────────────────────────────────────────────────────┘
```

加密的"不可读性"由加固 SDK 提供，签名的"唯一性"由自研 JNI 库提供。两者边界清楚——也正因如此，前者的安全性完全等于加固抗内存读取的能力。

## 3. 一次请求的链路

```
业务代码构造请求
  │
  ├─[1] 取策略：注解声明 / 无注解则查 URL 白名单
  │
  ├─[2] 头部签名：把当前请求头集合成结构化文本 → 加盐摘要 → 落到专用请求头
  │        （若策略要求，这一步的产物还会被再包一层信封）
  │
  ├─[3] 业务体：若类型是 JSON 且策略要求 → 整体包成信封；表单体不加密
  │
  ├─[4] 发请求
  │
  └─[5] 响应：若策略要求 → 解开信封 → 交回业务层
```

签在头与体两处，意味着任何一个参数被改动都会同时破坏两处，这是一种低成本的防篡改布局。它的有效性依赖一个前提：服务端必须用同一份字段集合重算。这个前提一旦不成立（字段集合漂移），就会出现客户端升级即全量报签名错误的问题。

## 4. 两层签名

```
会话级：绑定  会话标识 + 时间 + 用户标识   → 回答"这个请求是不是这个会话发的"
业务体级：绑定 业务实体字段集合           → 回答"业务参数有没有被替换"
第三份：同上的原文（不摘要）随体上传      → 只用于服务端排障回溯
```

- 盐由 native 层提供，不在资源文件里；
- 资源里另有一个兜底盐，但正常路径上不会被用到（native 调用没有失败）。

---

## 5. 信封结构

请求与响应使用同一类信封：密文块 + 摘要块 + 密钥材料块 + 版本标记。

两个可从设计层面确认的性质：

1. **客户端解不开自己发出的信封** —— 密钥材料是非对称封装的，私钥在服务端；
2. **响应只对当前会话可解** —— 换进程或换登录即失效。

结论：这套方案的定位是防旁路观察与防跨会话重放，而不是让内容在客户端不可见。任何在客户端完成的加密，其明文在客户端必然存在过。

---

## 6. 加固与可观测性的关系

这类加固对"是否有人尝试接近它"远比"被读走了多少"敏感。因此，任何以"接近后再读取"为特征的思路，本质上都是在和加固的检测面赛跑，而不是和加密强度赛跑。

这条判断对防守方同样成立：与其继续加固客户端，不如把密钥与判定搬到服务端（见 `REPORT.md` 第 5 节第 12 条）。
